❯ /speckit-constitution Python 3.12 managed with uv, FastAPI, Google Gemini     
through the google-genai SDK as the only LLM provider at runtime and in evals.  
Plain Python orchestration with direct function calls; no agent frameworks.     
ORCHESTRATION: a bounded supervisor loop, not a fixed pipeline. A Router plans: 
it returns a typed plan with ordered steps (agent and, for Knowledge, source    
rag or web), the user language as en or pt, and a standalone rewrite of the     
message that resolves references to earlier turns. The supervisor executes each 
step, records a structured observation (status, evidence, unanswered parts),    
and a critic reviews the observations: deterministic rules first, then a        
lite-model check that every part of the user message was answered. The critic   
may replan by adding, retrying or dropping steps; every plan revision and its   
reason is kept in the trace. The loop stops when the answer is complete, at     
MAX_SUPERVISOR_ITERATIONS, or when the per-request budget is spent. When more   
than one step answered, a synthesis step merges their answers into one draft    
that keeps every part. A final Personality step turns the draft into the answer 
the merchant reads, in the planned language and brand voice: it may shorten,    
merge repeated parts and drop details the user did not ask for, but it never    
adds a fact, number or URL and always keeps the ticket id and the facts that    
answer the question; code checks that every number and URL in the answer        
appears in the draft and that the ticket id is kept, and the eval judge checks  
that the asked facts survived; on violation or failure the draft is returned;   
deterministic refusals skip it. Sources are attached by code after Personality, 
and so is, when a cited source is from www.getnet.net, one short sentence in    
the answer language saying the global site may differ for Brazil. Each agent    
prompt lives in its own module and states role, scope, output format and        
refusal rules; the current date is injected by code. IDENTITY: every endpoint   
except health and metrics requires a Bearer JWT (HS256 with iss, aud, exp, sub  
and role merchant or operator) verified by code; the chat user_id must equal    
the token subject or the request gets 403; tools receive the merchant id from   
the authenticated principal, never from the LLM; conversations and tickets      
belong to their principal. Tokens are issued only by a CLI command, never by an 
endpoint. Raw user ids never reach logs or prompts: logs carry an HMAC          
pseudonym. MEMORY: conversations persist in SQLite on a Docker volume with      
turns, a rolling summary written by the lite model, and run checkpoints;        
follow-ups are resolved by the Router's standalone rewrite; a conversation      
survives a restart. HUMAN IN THE LOOP: escalation stores a checkpoint of the    
pending run, opens a ticket and returns status awaiting_human; operators list,  
claim atomically and resolve tickets by approve, edit or reject; resolving      
resumes the run from its checkpoint, passes the operator answer through         
Personality, appends it to the same conversation and writes an audit entry for  
every action. GUARDRAILS are deterministic first and run before any LLM: a      
message length limit; a message carrying a full card number (Luhn-valid) or a   
valid CPF is refused, and such values are masked in every field before they     
reach a log or the database; a message that names another merchant is refused;  
prompt-injection heuristics in English and Portuguese; the final answer passes  
a DLP check. Retrieved content and tool results are untrusted data, delimited   
in prompts and never followed or repeated as instructions. Unsafe or            
out-of-scope requests get a polite refusal; domain answers must be grounded in  
retrieved context with cited source URLs, and when grounding fails the system   
does not guess and escalates. MODELS, right model per task, all names and       
thinking levels from environment variables: planning, critic and memory summary 
use GEMINI_ROUTER_MODEL with thinking minimal; answering agents, synthesis and  
Personality use GEMINI_MODEL with thinking low, because the final text is what  
the merchant reads; embeddings use GEMINI_EMBEDDING_MODEL; the eval judge uses  
GEMINI_JUDGE_MODEL with thinking high and is never part of the request path.    
COST: every LLM call goes through one client wrapper that records model,        
latency, prompt, output and thinking tokens, cost in USD from a price table in  
environment variables including Google Search queries counted from grounding    
metadata, logs structured JSON with the request_id, applies a timeout and one   
retry on 429 or 5xx, preserves complete model content including thought         
signatures across tool turns, and enforces a per-request token budget. Google   
Search grounding and function calling never share a request. Limits are         
explicit and configurable: message length, top-k, tool iterations, supervisor   
iterations, token budget. Every LLM output that drives control flow is parsed   
into a Pydantic model; every tool returns a typed result and handles its own    
failures; when the budget is exceeded or the LLM stays unavailable, the API     
still returns valid JSON and escalates. ANSWER QUALITY is a requirement, not    
polish: correct facts in a hard-to-read answer count as a failure. Every answer 
is written for a Brazilian merchant reading on a phone: the first sentence      
answers the question; short, at most about 120 words unless the user asked for  
steps; numbered steps only for procedures; no markdown bold, headers or tables; 
one language, the planned one; no em dash or en dash; no talk about documents,  
retrieved context or the system (never "the documents do not contain"), though  
naming where a live value comes from, such as an exchange rate, is fine;        
nothing the user did not ask for; a comparison explains what each option is     
for, not only prices; Portuguese uses the merchant's words (maquininha, vendas, 
recebíveis, Pix) and English keeps the Getnet product names. Amounts and dates  
are formatted by code before any LLM sees them, in the answer language: pt R$   
1.250,00 and 25/11/2026, en R$ 1,250.00 and 25 Nov 2026; tools return raw       
values and a formatter renders them, so no answer shows an ISO date or an       
unformatted amount. Support answers explain in plain words what happened and    
what to do next, never a field-by-field status dump. Escalation and refusal     
messages say what happens next. Code enforces what can be checked: dashes       
replaced, markdown bold removed, no ISO date, answer language matching the      
plan; violations are logged and counted. OBSERVABILITY is implemented, not      
described: JSON logs with request_id, Prometheus metrics at /metrics, alert     
rules with promtool unit tests, a provisioned Grafana dashboard under a compose 
profile, health split into live and ready. EVALS are part of the product: a     
dataset with the official scenarios, compound, adversarial, authorization,      
multi-turn memory and human-in-the-loop flows; a runner against the live API    
with deterministic assertions, including the answer-quality checks above, plus  
an LLM judge with a typed rubric that scores clarity for a merchant next to     
correctness, groundedness, relevance and helpfulness, each with a threshold;    
the judge sees the same evidence the agents saw, including tool results and the 
list of web sources, each judgment runs with its own token budget, and the      
answer, evidence and verdicts in a report row always come from the same run;    
judge calibration against human labels; retrieval metrics; a sealed held-out    
set whose hash is committed before any code and which nobody opens during the   
session; the runner exits non-zero below thresholds and reports cost. TESTS:    
every functional requirement has an ID (FR-001, FR-002...) and at least one     
pytest test with the ID in its name; unit tests mock the LLM; integration tests 
call the HTTP API with the LLM stubbed at the wrapper. DELIVERY: runs with      
docker compose up and with plain docker build and docker run; non-root image,   
base image pinned by digest, uv lockfile installed frozen, healthcheck, log     
size limits; GitHub Actions runs lint, tests, a container smoke test and        
promtool on every push, and a live eval on tags; secrets only via .env with a   
committed .env.example. Simplicity over abstraction: build only what the spec   
and this constitution ask for. Each SDD phase (constitution, spec, plan, tasks) 
and each completed task gets its own commit on the repository default branch,   
with no feature or docs branches, pushed immediately, so the remote history     
proves the stages and their times. Scope of this phase: write the constitution  
from this text only, with no web research and no API calls; contracts get       
verified in the plan phase.
